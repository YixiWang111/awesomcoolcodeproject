# InkMirror — a writing analyser

Reads a folder of dated journal entries and shows their shape: how the vocabulary
moves over time, and which words come back without being noticed.

Built for **52685 Creative Coding, Assessment 1**. Application / Python project,
Weeks 7–11. Text analysis and visualisation only — no hardware, nothing real-time.

This README is the whole written deliverable. It contains the corpus statement, the
limitations note and the record of the submitted pitch, so there are no separate
documentation files.

## 1. The corpus — read this first

**There is no real journal in this repository.**

The project was pitched as an analysis of two years of the author's own writing. That
corpus does not exist: the author had not been keeping a diary, and could not produce
two years of dated entries that they were prepared to describe as their own.

What the pipeline runs on instead is `entries_sample/` — **275 generated entries
produced by `make_sample_corpus.py`**. They are a test fixture, not a record of
anyone's life.

### 1.1 Why it is declared rather than disguised

Two options were open. The first was to write plausible diary entries and present them
as a private journal. That was not taken, for three reasons:

1. **It would contradict the declaration already signed.** The submitted pitch deck's
   AI Declaration slide states that AI assistance was limited to writing support.
   Submitting machine-generated text as two years of personal journal entries would
   make that slide false.
2. **The claims would be unbackable.** The pitch says "I have been keeping a journal
   for two years" and "two years of text files, never once analysed". Asked to show
   the source files, there would be nothing to show.
3. **The findings would be circular.** The mood curve is what `mood_for()` in
   `make_sample_corpus.py` writes in. Reporting "polarity rose over two years" would
   be reporting a fact about the generator, dressed up as a fact about a person.

### 1.2 What the sample corpus is, precisely

| | |
|---|---|
| Generated by | `make_sample_corpus.py` |
| Random seed | `SEED = 42` (deterministic — reruns produce identical entries) |
| Entries | 275, one dated `.txt` file each |
| Period | 1 September 2024 → 29 August 2026 |
| Total words | 9,983 (mean 36.3 words per entry) |
| Cadence | 2–4 entries per week, irregular by design |
| Structure | `entries/YYYY-MM-DD.txt`, one entry per file |

Each entry's text is assembled from word pools selected by `mood_for(day)`, a scripted
curve combining a slow upward trend, a seasonal term, an exam-season penalty, and
deterministic jitter. **The corpus therefore carries a known signal by construction.**
That is the useful property, and it is what section 4 exploits.

### 1.3 What is real and what is not

| Real | Not real |
|---|---|
| Every line of the pipeline: loading, tokenising, scoring, statistics, figures | The entries themselves |
| The dates, the file format, the failure modes (empty files, undated files) | The claim that these dates correspond to days anyone lived |
| The sentiment scores — TextBlob did compute them from real text | The narrative they appear to describe |
| The validation result: the code does recover a known trend | The trend itself, which is a property of the generator |
| The negative results: 37% of entries match no topic keyword, 2 of 9 topics never fired, Flesch reading ease and sentence length move together | — |

**`output/run_report.md` is a description of the synthetic corpus.** Every CSV carries
a `source` column reading `synthetic_sample`, so a row copied out of a spreadsheet
still declares where it came from.

### 1.4 What the absence of a real corpus does and does not affect

**Does not affect:** the analyser. Nothing in `load.py`, `clean.py`, `sentiment.py`,
`lexical.py`, `visualise.py` or the three stretch-goal modules is tuned to the sample
corpus. The pipeline reads *a folder of dated `.txt` files*; it has no knowledge of
how they were written. Swapping the data does not change a line of analysis code.

**Does affect:** everything that would have been a claim about a person. This
repository supports the statement *"here is a working analyser, validated against a
known ground truth."* It does **not** support any statement about anyone's mood,
vocabulary habits, or how their two years actually went.

### 1.5 Swapping in a real journal

Three steps, no code changes:

1. Create `entries/` in the project root.
2. Put one `.txt` file per entry in it, named `YYYY-MM-DD.txt`. The date must be in
   the filename — the pipeline reads dates from filenames, not file metadata. Extra
   words after the date are fine (`2024-09-01 morning.txt` works). Files with no date
   in the name are skipped and reported, not silently dropped.
3. Re-run `python main.py`.

`config.corpus_dir()` prefers `entries/` whenever it exists and contains `.txt` files,
and falls back to `entries_sample/` otherwise. Every output — CSVs, figures,
`run_report.md` — then describes the real corpus, and the `source` column flips from
`synthetic_sample` to `private_journal` automatically. `validate_pipeline.py` will
report that it has been skipped, because a real journal has no known right answer.

## 2. What it does

```
entries/                     sentiment.py    ->  output/sentiment_scores.csv
 2024-09-01.txt     ──►      lexical.py      ->  output/lexical_stats.csv
 2024-09-02.txt              visualise.py    ->  output/word_frequencies.csv
 ...                                                   sentiment_timeline.png
                                                       wordcloud.png
                             validate_pipeline.py ->    validation.png
                                                       run_report.md

                             readability.py  ┐
  (stretch goals, optional)  compare.py      ├─>  output/stretch/
                             topics.py       ┘
```

One `.txt` file per entry, named with its date. The pipeline reads them in
chronological order, scores each one, counts the vocabulary, and draws two images.

**Everything in `output/` is the core deliverable. Everything in `output/stretch/` is
optional extra.** The three stretch goals are kept in their own folder so the boundary
of the declared scope stays visible in the file structure.

**Nothing is uploaded.** The whole analysis runs locally: `pathlib` reads the files,
and no entry text leaves the machine. This is a hard constraint of the project — a
private journal cannot be sent to an external service.

## 3. Running it

Requires **Python 3.12**.

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
python -c "import nltk; nltk.download('punkt_tab'); nltk.download('stopwords'); nltk.download('cmudict')"
python main.py
```

The fourth line downloads language data the analysis depends on. It is **not**
optional — see below.

### 3.1 Which NLTK resource is needed, and what breaks without it

| Resource | Needed by | If it is missing |
|---|---|---|
| `punkt_tab` | `clean.py` — every call to `word_tokenize` / `sent_tokenize` | **The pipeline does not run at all.** Raises `LookupError`. There is no fallback. |
| `stopwords` | `clean.py` — frequency counts and the word cloud | Runs, using a reduced built-in list, and prints a warning |
| `cmudict` | `textstat`, for the readability stretch goal only | Core pipeline is unaffected; the readability stage fails |

Two things worth being precise about, because the obvious setup command gets them
wrong:

- **It is `punkt_tab`, not `punkt`.** NLTK 3.9 changed the tokeniser's data layout, and
  `requirements.txt` pins nltk 3.10.3. Downloading only `punkt` still leaves the
  pipeline unable to tokenise.
- **`python -m textblob.download_corpora` is not needed.** TextBlob's default polarity
  score comes from a lexicon bundled inside the package. That command fetches `brown`,
  `movie_reviews` and `conll2000`, none of which this project reads. This was verified
  by running the full pipeline to completion with all three absent.

Note that the `stopwords` fallback is real but not a rescue: it lets the frequency
stage degrade gracefully, and then `content_words()` calls the tokeniser anyway. If
`punkt_tab` is missing, nothing runs regardless.

### 3.2 If the download fails

`nltk.download()` fetches from GitHub, which is unreachable on some networks. Since the
pipeline cannot run without `punkt_tab`, use a mirror — these three were confirmed
reachable, and none of them routes through GitHub:

| File | Size |
|---|---|
| `https://cdn.jsdelivr.net/gh/nltk/nltk_data@gh-pages/packages/tokenizers/punkt_tab.zip` | 4.2 MB |
| `https://cdn.jsdelivr.net/gh/nltk/nltk_data@gh-pages/packages/corpora/stopwords.zip` | 37 KB |
| `https://cdn.jsdelivr.net/gh/nltk/nltk_data@gh-pages/packages/corpora/cmudict.zip` | 875 KB |

Unzip each one and move the resulting folder into any directory NLTK searches, keeping
the category level:

```
C:\Users\<you>\AppData\Roaming\nltk_data\
    tokenizers\punkt_tab\
    corpora\stopwords\
    corpora\cmudict\
```

To see which directories NLTK searches on a given machine:

```powershell
python -c "import nltk; print(nltk.data.path)"
```

### 3.3 Other commands

To regenerate the placeholder corpus: `python make_sample_corpus.py`.

Each module also runs standalone, e.g. `python load.py` prints what it found.

## 4. Does the pipeline work?

There is one real advantage to a corpus you generated: you know the right answer.

`make_sample_corpus.py` builds each entry from word pools selected by a scripted mood
curve, so that curve is a known ground truth. `validate_pipeline.py` scores the corpus
with TextBlob and measures how closely the result tracks the curve it was built from.
It runs as the `CHECK` stage of `main.py` and writes `output/validation.png`.

Result on the current corpus:

| | r | |
|---|---|---|
| Per-entry | **+0.73** | strong |
| Smoothed trend (window 21) | **+0.97** | very strong |

**This proves the code works, not the method.** Because the entries were written from
mood-weighted word pools, a correlation is guaranteed by construction — the words were
chosen to carry the signal. What the result rules out is a bug between reading the
files and drawing the chart: dates parsing out of order, entries being dropped or
shuffled, smoothing running along the wrong axis. A *low* number here would be a real
alarm. A high one is the expected result, not a discovery.

It says nothing about whether a lexicon reads real writing well. On a real journal
there is no ground truth, and the module reports that and skips.

## 6. Stretch goals

The three extras declared in the pitch as "if ahead". They run automatically at the end
of `main.py` and write to `output/stretch/`. **Each is weaker than it looks**, and the
detail is in section 8.6 — the short version:

- **Readability** (`readability.py`) is mostly driven by sentence length, which the
  lexical statistics already measure. It is close to the same finding appearing twice
  rather than independent evidence.
- **The two-period comparison** (`compare.py`) splits at the midpoint entry. Nothing
  happened on that date, and re-splitting elsewhere would give different numbers.
  Nothing here reports how much they would move.
- **Topic tagging** (`topics.py`) is plain keyword matching. Its `topic_tags.csv`
  records which words triggered each tag, so a tagging decision can be audited. If you
  use this on a real journal, **edit `TOPIC_KEYWORDS` in `topics.py`** — out of the box
  those lists are a generic guess, and coverage swings from 99% to 20% depending on the
  `MIN_KEYWORD_HITS` setting.

`textstat` is needed for the readability module, and it needs NLTK's `cmudict`
dictionary for syllable counts:

```powershell
python -c "import nltk; nltk.download('cmudict')"
```

## 7. Design decisions

**Stopwords are removed for counting but kept for scoring.** Frequency analysis without
stopword removal returns `the`, `and`, `I` at the top and tells you nothing. But
sentiment scoring needs them: negation and pronouns carry meaning, and "I am not happy"
is not "happy". So `clean.py` exposes two functions, `content_words()` and `tokens()`,
and each stage uses the one it needs.

**The sentiment colour scale is blue/red, not green/red.** Polarity has a real zero and
two opposite poles, so it takes a diverging scale. Green/red is the obvious choice and
the wrong one — it is the most common form of colour blindness, and the two poles
collapse into each other under it. Blue/red was checked against a colour-vision
simulation before use (CVD ΔE 21.6, normal-vision ΔE 32.3). Points are also faded
according to how much their score can be trusted, so reliability is carried by opacity
as well as colour.

**Blue and red are reserved for polarity, so the period bars are grey.** In the
stretch-goal comparison, "first half" and "second half" are a plain before/after
grouping, not a positive/negative one. Colouring them blue and red would carry the
sentiment meaning into a chart where it does not apply, so they take two shades of a
single neutral hue instead — validated as an ordinal ramp.

**Provenance is a column, not a header comment.** Every CSV carries a `source` field on
every row, so a single row copied out of context still declares whether it came from
the synthetic sample or a private journal. Provenance that can be lost by copying is
not provenance.

## 8. Limitations

What this analysis can and cannot support, and what would be needed to close each gap.

The single most important line in this document: **the polarity score measures the
vocabulary of an entry, not the mood of the person who wrote it.** Everything below is
an elaboration of that sentence.

### 8.1 Limitations of the sentiment method

**8.1.1 It is a dictionary, not an understanding.** TextBlob's `polarity` is a lexicon
lookup. Each word is matched against a fixed dictionary of pre-scored words, the scores
are averaged, and the result is a number in [-1, 1]. The program has no model of what
the sentence means. Consequences:

- **Word order is invisible.** "I am happy, considering what happened" and "I am
  considering what happened, happy" score identically.
- **Negation scope is invisible.** The lexicon scores `not` negatively rather than
  flipping what follows it, so "not unhappy" is not treated correctly.
- **Intensifiers are crude.** "slightly worried" and "worried" can land close together,
  while "devastated" and "upset" may not be ordered as a reader would put them.

**8.1.2 Irony, understatement and self-deprecation read as their surface.** This is the
most damaging failure for a journal specifically. Personal writing is full of lines like
*"brilliant, another four hours of sleep"* or *"well, that went beautifully"*, where the
intended meaning is the opposite of the words. The lexicon scores those positive. A
writer who habitually uses dry understatement will show a systematically **inflated**
polarity score, and the flatter their humour, the larger the error. There is no fix for
this within the current scope. It would require a model with contextual understanding,
which is exactly what the pitch chose to avoid.

**8.1.3 The lexicon was not built for diaries.** The pre-scored vocabulary behind this
kind of analysis is derived mainly from product reviews, film reviews and general prose.
It does not contain the specific register of a private journal: neither the mundane
vocabulary of daily routine, nor the particular weight that a private writer gives an
ordinary word. A word like `heavy`, which in this corpus carries the whole sense of a
bad day, is not reliably scored as negative by a general-purpose lexicon.

**8.1.4 One number cannot hold a mixed entry.** An entry that is genuinely ambivalent —
a hard day that the author is also grateful for — is compressed to a single value near
zero. That value then looks identical to an entry that simply has no feeling in it at
all. **Neutral is ambiguous: it means either "no signal" or "cancelled-out signal", and
the method cannot tell you which.**

**8.1.5 Short entries are unstable.** A twenty-word entry can be swung from positive to
negative by one word. This is mitigated in the visualisation by fading points according
to how much they can be trusted, and by reporting the count of low-confidence scores,
but the score itself is not corrected. Fading a point does not make it more reliable; it
only stops it from being read as equal to the rest.

**8.1.6 Subjectivity is a separate axis, and both are reported.** `subjectivity` (0 to
1) is reported alongside polarity because a polarity computed from an entry with few
opinionated words is close to meaningless. A score of +0.5 built on two charged words
and a score of +0.5 built on a paragraph of them are not the same finding, and the
second number is what distinguishes them.

### 8.2 Limitations of the corpus

**8.2.1 There is no real corpus — the current data is generated.** This is the largest
limitation in the project, and it comes before all the others. `entries/` does not
exist, so the pipeline reads `entries_sample/` — 275 synthetic entries produced from a
scripted mood curve. **Every figure and number currently in `output/` describes that
synthetic data.**

Two consequences, and they are different in kind from everything else in this section:

- **No claim about a person can be made from this run.** The mean polarity of +0.121,
  the +0.112 shift between halves, the word cloud, the topic heatmap — none of these
  are findings about anyone. They are facts about a generator.
- **The results are circular by construction.** Each entry is written from word pools
  selected by `mood_for(day)`. Reporting "polarity rose across the two years" would be
  reporting back the curve that was fed in. The finding is not merely weak; it is a
  tautology.

**8.2.2 What a generated corpus can and cannot be used for.** It can be used to **test
the code**, and that is the one real advantage of a corpus you generated yourself: the
right answer is known. `validate_pipeline.py` recovers per-entry **r = +0.73** and
smoothed **r = +0.97**. That result is worth exactly one thing: it rules out a bug
between reading the files and drawing the chart. Because the entries were written from
mood-weighted word pools, a high correlation is guaranteed by construction. It is the
expected result, not a discovery, and it is **not** evidence that a lexicon reads real
writing well. It cannot be used to learn anything about a person, for the reasons in
8.2.1.

**8.2.3 The diary would be a biased sample of the two years.** *Sections 8.2.3–8.2.5
describe limitations that would apply to a real journal. They are listed because they
will apply as soon as `entries/` is populated.* People write when something has
happened. Days that were uneventful are under-represented, and hard days are
over-represented — writing is itself a way of coping. A journal corpus is therefore not
a random sample of the author's days, and a mean polarity calculated over it is **not**
an estimate of how the time actually felt. This bias is structural and cannot be
corrected after the fact, because the missing days were never written down.

**8.2.4 Entries are irregularly spaced.** There may be three entries in one week and
none for ten days. The data is a sequence of entries, not an evenly sampled time series,
so the usual statistical machinery for trends does not apply. The smoothed line in the
timeline averages over a fixed number of **entries** rather than a fixed span of
**time**, which keeps each point equally supported but means the line's horizontal
position does not carry a consistent temporal weight.

**8.2.5 Two years is not enough to claim a trend.** A "trend" across two years of one
person's writing is a very small sample, and there is no control. Any movement in the
line could equally be a change in writing habits, a change in what was worth writing
about, or noise.

### 8.3 Limitations of the analysis

**8.3.1 The smoothed line is descriptive, not inferential.** The moving average is a
display device. It has no confidence interval, no significance test, and no model behind
it. A visible rise is a visible rise — it is not evidence of a real change, and the run
report deliberately reports mean polarity per calendar year as a headline only, not as
the side-by-side period comparison listed as a stretch goal.

**8.3.2 Frequent words conflate habit with subject matter.** A word can be frequent
because the author reaches for it unconsciously, or simply because the thing it names
came up a great deal. `walk` at the top of the frequency list may mean a verbal tic or
may mean a lot of walking. The frequency table shows what is there; it does not
distinguish between the two explanations.

**8.3.3 Preprocessing choices shape the result.** Stopword removal, the minimum token
length, contraction expansion and the decision to keep negations (`not`, `never`, `no`)
in the frequency count all change the output. Different, equally defensible choices
would produce a different word cloud. The current settings are documented in `config.py`
and `clean.py`; they are choices, not neutral defaults.

**8.3.4 There is no comparison baseline.** The word cloud shows which words recur, but
not whether that vocabulary is narrow. "These are my most frequent words" and "I use a
small vocabulary" are different claims, and only the first is supported. Answering the
second would need a comparison corpus — other people's diaries, or the author's own
academic writing — which is outside the scope.

### 8.4 Limitations of interpretation

**8.4.1 Quantifying the journal risks taking the metric for the truth.** The premise of
the project is that an author cannot see their own patterns. But the thing the code
produces is not the pattern — it is a *proxy* for the pattern, built from a
general-purpose lexicon. Turning a private journal into numbers makes it measurable, and
measurability is persuasive. A rising line on a chart is far more convincing than it
deserves to be given a lexicon average over 275 short entries. The honest position is
that this tool can suggest where to look, and cannot tell anyone how they felt.

**8.4.2 The founding premise is itself unverified.** The project assumes that an
author's own reading of their journal is unreliable and that the analysis will reveal
something they cannot see. That assumption is untested. It could equally turn out that
the analysis recovers only what the author already knew, at the cost of a great deal of
context. Nothing in the current build would detect that outcome.

**8.4.3 Privacy boundary.** The analysis runs entirely locally: `pathlib` reads the
files, and nothing is uploaded or sent anywhere. This is a design constraint rather than
a limitation, and it is the reason the project can be done at all — a private journal
cannot be sent to an external service. It is listed here because it constrains the
method: **cloud-based models that would fix the irony and context problems in 8.1.2 are
ruled out by it.**

### 8.5 Scope

Deliberately excluded, as declared in the pitch:

- **One polarity score only.** No emotion classification, no second sentiment axis.
- **English only.** No multilingual handling.
- **No hardware, nothing real-time.**
- **A fixed set of outputs**: one timeline, one word cloud, two CSVs.

The three stretch goals named in the pitch are implemented in `readability.py`,
`compare.py` and `topics.py`. They run as a stage at the end of `main.py` and write to
`output/stretch/`, **not** alongside the core results. That separation is deliberate.
The pitch declared these as "if ahead" extras, and keeping them in a different folder
means the boundary of the assessed scope stays visible in the file structure rather than
quietly blurring into the main work.

### 8.6 Additional limitations of the stretch goals

**8.6.1 Readability scores were built for school textbooks.** Flesch reading ease and
Flesch-Kincaid grade were designed to answer *"what age is this text suitable for?"* A
private journal has no target audience and no reading age. Applied to one, the formulas
measure something adjacent to what they were built for. Worse, they are not independent
evidence. Both are computed almost entirely from **average sentence length** and
**average syllables per word** — which means a change in Flesch grade and a change in
mean sentence length are largely *the same finding seen twice*. Presenting them as two
confirmations of one conclusion would be double-counting. The whole spread of scores in
this corpus (25 to 100) partly reflects how short some entries are rather than how they
are written.

**8.6.2 The period split is arbitrary, and there is only one of it.** The two halves are
split at the midpoint entry. Nothing happened on that date — it is simply the middle of
the data. Consequences:

- A real change that **straddles the boundary** is split across both halves and
  cancelled out.
- A change that happens to sit **inside one half** is attributed to "the period" as a
  whole, even if it lasted three weeks.
- Because the split is a single fixed point, there is **no way to tell** whether the
  differences found are real or an artefact of where the line was drawn. Re-splitting at
  a different date would give different numbers, and nothing here reports how much they
  would move.

The comparison is also **descriptive only**. No significance test is run, and with one
person's journal there is no meaningful control group to run one against.

**8.6.3 Topic tagging only finds words someone guessed in advance.** The tagging is a
`word in list` test against `TOPIC_KEYWORDS`. It has no model and no evaluation. A topic
is found only if the writer's word for a thing happens to be on the list. The coverage
number is the honest headline, and it is unstable:

| Minimum keyword hits | Entries tagged |
|---|---|
| 1 | 99% |
| 2 (default) | 63% |
| 3 | 20% |

**The same journal, the same keywords, and coverage moves from 99% to 20% on the
strength of one setting.** At 1 hit, a single stray word tags an entry and the tags stop
distinguishing anything; at 3, most entries go untagged. There is no correct value, and
the reported result is an artefact of a number chosen by hand. Two further problems:

- **Absence of a keyword is not absence of the topic.** An entry about loneliness that
  never uses any of the words on the list is invisible, and 37% of entries in the
  current corpus match nothing at all.
- **Words are ambiguous.** `light` is on the weather list and also means "not heavy",
  which this corpus uses frequently. The tagger cannot tell them apart.

The output should be read as a rough index into the journal, not as a finding about it.

### 8.7 What would actually fix these

| Limitation | What it would take |
|---|---|
| **No real corpus at all (8.2.1)** | **Real entries written before reading anything about sentiment analysis. Nothing else on this list can be settled until this one is.** |
| Irony, negation scope, context (8.1.1–8.1.2) | A contextual language model — ruled out by the privacy boundary in 8.4.3, or run fully locally |
| Lexicon not built for diaries (8.1.3) | Hand-scoring a sample of entries and comparing against the lexicon, to measure the error directly |
| Mixed entries collapsed to one number (8.1.4) | Report the spread of sentence-level scores within an entry, not just the mean |
| Unstable short entries (8.1.5) | Weight the mean by entry length, or exclude entries below a threshold and say so |
| No baseline for "narrow vocabulary" (8.3.4) | A comparison corpus |
| Irregular sampling (8.2.4) | Resample onto calendar weeks and accept the resulting gaps, or model the spacing explicitly |
| Diary selection bias (8.2.3) | Not fixable after the fact — the unwritten days do not exist |
| Trend is not significant (8.2.5, 8.3.1) | More years, and a method with a stated uncertainty rather than a moving average |
| Readability counts sentence length twice (8.6.1) | Report only one of them, or report readability alone and drop the sentence-length panel |
| Split date is arbitrary (8.6.2) | Re-run the comparison at several split points and report the spread; if the difference moves around, it was never there |
| Tags depend on the hit threshold (8.6.3) | Report coverage across thresholds (done), and hand-check a sample of tagged entries against the actual text |

## 9. Statement on the submitted pitch

The pitch (speech script and slide deck) was submitted on **21 August 2026**, before the
corpus problem was understood. This section records which parts of it this repository
can and cannot support. **The local copies of those two files have since been removed
from this folder; removing them here does not retract what was submitted.**

### 9.1 The one claim that has to go

**That the corpus is the author's own.** Everything else in the pitch holds: the project
type, the environment, the resources, the five-week timeline, the scope limits and the
stretch goals are all accurate, and the prototype implements all of them.

Passages affected:

| Where | What it says | Status |
|---|---|---|
| Speech §1 | "It analyses my two years of journals and essays…" | Not supported |
| Speech §2 | "I have been keeping a journal for two years, and I have almost no idea about its form." | Not supported |
| Speech §5 | "…in week 11, it's all put together on my real data set" | Not supported |
| Deck slide 2 | "2 years of personal writing waiting to be read back as data" / "Two years of text files, never once analysed." | Not supported |
| Deck slide 5 | "WEEK 11 — Run on the real corpus, write limitations note" | Run is on the test corpus |
| Deck slide 3 | "The analysis runs entirely offline… my journal is never uploaded anywhere." | **Still true** — no network calls are made |
| Deck slide 6 | AI Declaration: use "limited to writing support" | **Still true, and it is the reason the corpus is declared** |

### 9.2 Wording to use instead

**Speech §1:**

> "My project is InkMirror. It analyses a two-year corpus of dated diary entries as if a
> computer were reading them, and shows the form of the writing — the sentiment trend
> over time and the vocabulary habits underneath it. The corpus it is running on today
> is a generated test set; the analyser itself is built to read any folder of dated
> entries."

**Speech §2** — keep the problem, state the gap:

> "The problem I set out to solve is that a writer cannot see their own patterns. I read
> my own work as its author, not as an observer, and tone and vocabulary are exactly
> what a writer is least able to see. The honest complication is that I could not
> assemble two years of my own entries in time to build against. So I built the analyser
> first and tested it against a corpus generated from a known mood curve. That gave me
> something a real journal cannot: a right answer to check the code against."

**Speech §5:**

> "…and in week 11 it all runs end to end, on a generated test corpus, because that is
> the corpus I have. Every stage reads a folder of dated text files and knows nothing
> about how they were written, so the real journal can be dropped in later without
> changing a line of analysis code."

**Deck slide 2** — replace the body's first clause ("I have kept a journal for two years
and written a great deal for university, and I have almost no sense of the shape of any
of it") with "A writer cannot see the shape of their own work." The rest of the slide is
already written in general terms and stays true. Replace the "2 years of personal
writing" call-out with "2 years of dated entries, generated from a known mood curve — a
right answer the analyser can be checked against", and the margin note with "**The
analyser is already general** — it reads any folder of dated text files, plain
`YYYY-MM-DD.txt`, with no code change."

**Deck slide 5:** "Run end to end on the test corpus, write limitations note".

**Deck slide 3:** change "my journal is never uploaded anywhere" to "**the entries** are
never uploaded anywhere". One word, and it is exact.

**Deck slide 6 — no change.** The declaration is accurate as written, and it stays
accurate only if the corpus is labelled as generated. If generated entries were
submitted as two years of personal journalling, generative AI would have authored the
*primary data* the whole project rests on — the opposite of "writing support", and a
direct contradiction of a declaration already signed.

### 9.3 If asked directly

> "The pitch was written around a journal I was going to build against. I couldn't get
> two years of entries together in time. Rather than fake the dataset, I built the
> analyser and tested it against a corpus generated from a known curve — which means I
> can show the pipeline recovers a trend it was built from, r = 0.97 smoothed, and I can
> show exactly which parts of a real analysis I can't support yet. The corpus situation
> is documented in the README."

### 9.4 Why this is the stronger submission

The alternative — generated entries passed off as a private journal — fails in three
concrete ways, and each is a question an assessor can ask:

| | Pretend journal | Declared test corpus |
|---|---|---|
| "Show me an entry." | Nothing to show | `entries_sample/` — 275 files, reproducible from `SEED = 42` |
| "What does r = 0.97 prove?" | Nothing; there is no ground truth | That the code has no bug from file to chart |
| "Where did the data come from?" | Cannot answer | `make_sample_corpus.py`, and section 1 says so |
| AI Declaration | Contradicted | Consistent |

A prototype that runs, that is validated against a known answer, that states plainly what
it cannot yet claim, and whose only gap is the dataset it was always designed to accept —
that is a defensible piece of engineering.
